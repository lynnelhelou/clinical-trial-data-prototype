# Clinical Trial Data Quality and Audit Prototype

A small SQL + Python prototype showing how clinical trial data can be validated, corrected, and tracked. **All data is synthetic**, generated by a script. This is a self-directed learning project, not real clinical work.


## Scenario

A fictional sponsor is running a 5-visit trial at 10 sites with 500 participants. Data entry is inconsistent. The goal: define the data model and rules, catch bad data automatically, show which sites need help, and keep a trustworthy record of every change.

## What it includes

| Piece | File | What it shows |
|---|---|---|
| Data model | `schema.sql`, `data_dictionary.md` | Sites, participants, visits, measurements, with keys and constraints |
| Configurable rules | `reference_ranges`, `allowed_transitions` tables | Rules stored as data so they can be changed without rewriting code |
| Synthetic data | `generate_data.py` | 500 participants (+ 8 planted duplicate registrations), 2,500 visits, plus 163 deliberately planted errors |
| Validation checks | `checks.sql`, `run_checks.py` | 6 checks, compared against the planted-error answer key |
| Audit trail | triggers in `schema.sql` | Automatic log of who changed what, when, and why |
| Workflow rules | `trg_status_transition`, `workflow_demo.py` | Illegal participant status changes are blocked |
| Site monitoring | `output/site_report.csv` | Issues per 100 completed visits, by site |

## How to run

```bash
pip install -r requirements.txt
python generate_data.py
python run_checks.py
python workflow_demo.py
```

## Validation checks

1. **Missing required values:** a completed visit must have all four measurements.
2. **Out of range:** values outside `reference_ranges`.
3. **Diastolic >= systolic:** physiologically impossible.
4. **Out of visit window:** visit more than 3 days from its scheduled date.
5. **Duplicate participants:** same site, birth date, sex, and enrollment date under two IDs.
6. **Status mismatch:** marked Completed without 5 completed visits.

## Results

- The six checks found all 163 planted errors, and the flagged records matched the answer key exactly (see `output/check_vs_answer_key.csv`). This shows the checks work as designed on this dataset, not that they would catch every real-world problem.
- Sites 3 and 7 had the highest issue rates, at 16.0 and 15.6 issues per 100 completed visits, compared with 3.8 to 10.3 at the other sites. The generator deliberately gave these two sites more errors, so this confirms the report can surface problem sites.
- Missing required values were the most common issue (50 of 163), followed by out-of-window visits (40) and out-of-range values (30).
- The workflow demo blocked an illegal status change (Screening to Completed), logged a data correction with the user and reason, and rejected attempts to edit or delete audit history.

## Design decisions

- **Checks flag bad data instead of blocking it.** The tables allow out-of-range values on purpose. In many clinical data systems, data is accepted at entry and then raised as a query for someone to review, instead of being rejected outright. I reserved hard blocks for things that are never valid, like an illegal status change
- **Rules live in tables**, so a study team can change a range or a workflow without editing queries.
- **Audit log is append-only** (enforced with triggers). In a production database like PostgreSQL, this would also be enforced with permissions.

## Limitations

- Synthetic data: error patterns are simplified and the sites were given different error rates on purpose.
- SQLite has no real database users, so "who" comes from a `session_context` table the application sets.
- Anyone with direct access to the SQLite file could bypass the triggers. This demonstrates the concept, not full regulatory compliance.
- Not electronic signatures, validation documentation, or any other formal compliance requirement.
